# 星枢 Matrix 开发规范与工作方法

## 一、工作方法
1. **先读后改**：动手前先读相关模块的后端代码、前端页面和接口文档，并对运行中的沙箱实例发只读请求，弄清现状（实时数据、演示数据、空壳、隐藏入口），再决定改法。
2. **对标再落地**：交互和信息组织参考 KubeSphere / Rainbond / JumpServer / 夜莺 / PagerDuty。做得好的直接借鉴；星枢自己的差异化能力（审批流、堡垒机、需求→AI 开发、智能诊断）保留。
3. **小步提交、逐项验证**：一次只做一项，做完就跑格式检查、静态检查和单元测试，再部署到沙箱 k3s 实测，最后在浏览器里走一遍流程。
4. **并行分工**：大块工作按模块拆给并行子任务。每个子任务只写自己的模块目录和接口文档，不碰入口文件，不做 git 操作；入口与路由由主线统一合并，避免冲突。
5. **如实汇报**：每次交付都写清已验证什么、怎么验证的、还有哪些没验证（真实 IdP、真实短信或邮件服务商、真实 AD、预发联调等），不说「生产可用」。
6. **分支纪律**：新功能放 feature 分支，beta 只在你确认后合并；不强推。按你这次的要求，改完先部署给你看，不提交。

## 二、后端（Go）
- **结构**：`internal/modules/<模块>` 按 handler → service → store 分层；跨模块只通过接口或事件交互，不直接读别人的表。
- **接口**：REST 风格，统一前缀 `/api/v1`；统一错误结构（`httpx.BadRequest` / `Forbidden` / `Conflict` 等，错误信息用中文）；列表接口支持分页和筛选。
- **权限与审计**：每个路由都挂 `rbac.RequirePerm`；所有变更都写审计日志（操作人、对象、前后差异、原因）；生产环境的高危变更走审批流。
- **数据库**：每次结构变更都在模块的 `migrations/` 下新增一个编号迁移，旧迁移一律不改；约束（CHECK、唯一、外键）写在数据库层。
- **安全**：密码、私钥、Token 用 AES-GCM 加密存储，接口只返回脱敏值；外部 URL 做防 SSRF 校验；LDAP、SQL、Shell 参数都要转义或参数化，防注入；令牌一次性、有有效期；不信任请求头里的来源地址。
- **可靠性**：外部调用一律带 `context` 超时；涉及多步的变更（比如改密）先写待定状态，验证成功后才转正，失败时能判断真实状态；后台任务要能重入。
- **质量门禁**：`gofmt -l` 为空，`go vet` 和 `go test` 通过；新逻辑必须有单元测试（成功、失败、边界、注入用例）。

## 三、前端
- **技术**：原生 JS，每个功能一个 IIFE 模块（`xs-<功能>.js`），挂到 `window`；统一用 `XS.api` 调接口，出错时显示中文提示。
- **界面**：KubeSphere 风格的浅色企业界面，不用光效和渐变；全部中文；不出现接口路径等开发术语；没做完的功能在实时模式下隐藏，不放空壳。
- **表单**：统一用 formkit（分步向导、AI 一句话填写、YAML 双向编辑、表单内测试），字段旁就地校验；密码和密钥字段不发给模型。
- **危险操作**：删除和执行变更必须二次确认；高危删除（命名空间、集群、数据库）要输入资源名称才能确认；系统资源（如 kube-system）不提供删除。
- **安全**：所有用户输入渲染前转义（`esc()`），不拼接未转义的 HTML。
- **质量门禁**：`node --check`；用 Playwright 跑关键流程和全量路由回归，截图检查是否溢出、截断，配色对比度是否够。

## 四、文档
- 每个模块维护 `docs/api/<模块>.md`：接口、字段、权限、错误码、未验证项。
- 每个版本更新 `CHANGELOG.md` 和 README 中的版本号；对标进度写在 `docs/benchmark-kubesphere-rainbond.md`。
